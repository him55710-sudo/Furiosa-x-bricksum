# 자가 발전 학습 모듈

2026-09-28 · 연구에 근거한 실행 가능한 별도 프로토타입 · 실제 사용자 검증 전

**배울 것은 사용자의 선택이고, 바꿀 것은 상품의 추천 순위다. 예산과 결제 권한은 학습 대상에 넣지 않는다.**

Consensus에서 찾은 연구와 GitHub의 APReL·choix 소스를 확인하고, 현재 Node 백엔드에서 실행할 수 있는 베이지안 비교 선호 모듈을 만들었다. APReL 전체를 설치한 제품이 아니라, 공개 구현의 선형 softmax·정보이득 원리를 참고해 별도로 작성한 작은 JavaScript 구현이다. [출처와 선택 근거](RESEARCH.ko.md), [라이선스](THIRD_PARTY_NOTICES.md).

## 바로 실행

프로젝트 루트에서 실행한다. 코어 모델은 Node 내장 기능만 사용한다. 서명 경계 테스트와 데모는 프로젝트에 이미 있는 `ethers`가 필요하다.

```powershell
node --test learning/tests/*.test.mjs
node learning/demo.mjs
node learning/simulate.mjs
node learning/verify-artifacts.mjs
```

- [demo.json](artifacts/demo.json): 가상 사용자의 질문·응답, 전후 가중치, 불확실성, 제외된 상품, 통제 추가, 상태 복원 결과.
- [합성 실험 결과](artifacts/simulation.ko.md): 비교 기준, 실패 상황, 질문 전략, 격자 민감도.
- [simulation.json](artifacts/simulation.json): 사용자별 원시 지표, 모든 seed, 검증 설정 비교, 실행 코드 해시.
- [테스트 실행 기록](artifacts/tests.tap): 26개 테스트 통과. [원문·산출물 검증](artifacts/verification.json): 해시·저장 상태 복원·로컬 링크 확인.
- [수식과 숫자 설정](ALGORITHM.ko.md): 어떤 증거가 무엇을 얼마나 바꾸는지.
- [백엔드 연결 계약](INTEGRATION.ko.md): 실제 앱에 연결할 위치와 현재 구현 범위.

데모는 로컬 서명 검증만 수행한다. 제출 거래 0건, Kiln 호출 0건이다. 합성 응답을 실제 사용자의 응답으로 저장해서는 안 된다. 기존 웹 화면이나 결제 실행 경로에 자동 연결하지 않았으며, 해당 부분의 앱 구현과는 분리해 검토할 수 있다.

## 처음 이해할 세 가지

| 상태 | 받아들이는 증거 | 바뀌는 것 |
|---|---|---|
| Hard Control | 사용자가 승인한 정책 | 학습 모듈에서 변경하지 않음 |
| Control Memory | 유효한 판매자 서명과, 수수료 때문에 한도를 넘었다는 검증 결과 | 해당 사용자·목적·판매자에 최종 총액 견적 요구 추가 |
| Preference Model | 인증된 사용자가 제시된 A/B 중 직접 고른 결과 | 가능한 취향 가중치들의 확률과 추천 순위 |

“A보다 B를 골랐다”는 사실은 “환불을 정확히 15% 더 중요하게 생각한다”와 다르다. 가격·환불·수량이 동시에 다른 경우 여러 설명이 가능하다. 모델은 그 설명들을 함께 남겨두고, 새 선택이 들어올 때 더 잘 설명하는 가중치에 확률을 더 준다.

그래서 `환불 = +1.5`, `학습률 = 0.1`, `confidence = 0.82`를 근거 없이 고정하지 않는다. 가중치 평균과 구간, 후보를 잘못 골랐을 때의 예상 손해를 함께 반환한다. 이 손해는 **0~1로 정의한 선호 효용 차이**이며 원화 손실이나 결제 실패 확률이 아니다.

## 실행 결과를 읽는 예

현재 데모에서 환불을 중시하는 **가상 사용자**의 비교 8회를 넣었을 때:

| 특성 | 처음 평균 | 8회 뒤 평균 | 95% 주변 사후 구간 |
|---|---:|---:|---|
| 저렴함 | 0.3333 | 0.1987 | 0.00~0.65 |
| 환불 가능성 | 0.3333 | 0.6733 | 0.25~1.00 |
| 수량 | 0.3333 | 0.1279 | 0.00~0.45 |

환불을 더 선호한다는 방향은 배웠지만, 정확한 비율은 아직 넓게 불확실하다. 이는 환불 가중치가 실세계에서 67.33%임을 입증한 결과가 아니다. 최종 상태는 `DEFER_TO_USER`이며 `paymentAuthorized=false`다.

합성 평가의 정상 조건에서는 평균 후회값이 균등 가중치 0.0435에서 이 모델 0.0237로 감소했다. 그러나 학습 후 취향을 바꾼 조건에서는 0.0728에서 0.1160으로 악화했다. 기존 질문 12회 조건에서는 정보이득 질문의 평균 log loss가 임의 질문보다 높았지만, 사용자별 짝 bootstrap 구간이 0을 포함하여 차이를 구분하지 못했다. 이 반례와 불확실성을 결과 파일에 포함했다. **현재 결과로 실제 고객 성과 개선이나 자동 구매의 적합성을 주장하지 않는다.**

## Grok 검토 이후 추가된 기능

[첫 검토와 반영 기록](review/ROUND-001.ko.md)에 채택·정정 이유를 남겼다. `beginPreferenceEpoch`로 사용자가 명시적으로 취향 변경을 선언하면 기존 학습을 보존하고 새 사전분포에서 시작한다. 이전 질문과 이전 epoch의 승인으로 새 학습을 진행할 수 없다. 자동 변화 탐지 기능은 아니다.

질문 목표는 이제 호출자가 반드시 명시한다. 기존 전체 정보이득과 가중치 w만의 정보이득을 분리해 비교했고, 신규 24개 seed의 질문 12회 결과도 임의 질문 대비 우월성을 확인하지 못했다. 적정량 선호·환불 가치 포화 조건과 사용자 단위 오차 구간도 추가했다. [확장 실험 계획](review/EXPERIMENT-V2.ko.md)은 실행 전에 작성했지만, v1 결과를 본 뒤 설계한 탐색적 후속 연구다.

[2차 검토](review/ROUND-002.ko.md)에서는 오래된 저장본의 복원으로 이전 승인이 살아날 수 있는 경로를 보완했다. 모델과 분리된 SQLite `EpochAuthority`로 현재 세대를 확인한다. 이 저장소가 없는 오프라인 profile은 자동 제안 준비 상태를 반환하지 않는다. 기존 증거에 **같은 새 응답을 이어 붙이는 비교군**도 추가해 리셋과 단순 재학습을 구분했다.

현재 확인한 실행 환경은 Node 24.19.0이다. epoch 저장소는 Node 내장 `node:sqlite`를 사용한다. 반복 검토는 이 채팅에 연결된 30분 간격 확인으로 이어가며, 새 근거·구체적 미완료 작업이 있을 때만 Grok에 후속 검토를 보낸다. [운영 절차](review/WORKFLOW.ko.md).
