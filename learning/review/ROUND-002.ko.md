# Grok 학습 모듈 검토 2차

2026-09-28 · marker `GROK-LEARNING-R2`

Grok는 1차 응답의 중복 지적·표본 수·과도한 일반화를 정정했고, 늦은 응답과 저장본 롤백이라는 두 가지 추가 가설을 제시했다. 아래는 직접 코드를 점검하고 테스트한 판정이다.

## E1: 늦은 응답의 epoch 오인

현재 `answer()`는 동기 함수이며 질문을 조회한 후 모델 반영까지 `await`가 없다. epoch 시작 시 질문 레지스트리를 지우므로 이전 질문 답변은 원래도 거부됐다. 따라서 제시된 비동기 경합을 기존 로컬 함수의 재현된 버그로 분류하지 않는다.

방어를 명확하게 하기 위해 evidence의 epoch를 현재 시각이 아니라 **저장된 질문의 발급 epoch**에서 가져오고 현재 epoch와 일치하는지 검사하도록 바꿨다. 인증/검증을 기다리는 외부 Promise 사이에 epoch 전환을 넣는 회귀 테스트도 추가했다. 늦은 응답은 거부되며 새 사후분포 해시는 유지된다.

## E2: 이전 snapshot을 복원하면 이전 epoch가 되살아남

채택했다. 모델 snapshot은 자신이 최신인지 알 수 없으므로, snapshot 내부 ID 비교만으로는 롤백을 막지 못한다.

[EpochAuthority](../epoch-authority.mjs)는 모델 저장본과 분리된 SQLite 현재 epoch 포인터·단조 sequence·전환 기록을 유지한다. 초기 등록은 현재 epoch를 덮어쓰지 않으며, 전환은 현재 stamp 비교와 다음 sequence 기록을 같은 트랜잭션으로 처리한다. 저장소가 연결된 profile은 질문·응답·판정 시 현재 epoch를 다시 확인한다.

저장소가 없는 순수 오프라인 profile은 `READY_TO_PROPOSE`를 반환할 수 없다. 제안에는 scope·epoch ID/sequence·모델 해시를 넣고 `checkProposalFreshness()`로 다시 검사한다. 이 함수는 선호 상태의 최신성 검사이며 결제 승인은 아니다.

회귀 테스트로 오래된 모델·정책·제안·worker를 거부하는지 확인했다. 독립 SQLite 연결과 DB 재개방 후에도 현재 epoch가 유지되고 오래된 snapshot 복원이 거부된다. 원본 authority DB 자체를 백업으로 되돌리는 운영자 행위나 파일 변조까지 막는 암호학적 원장은 아니다.

## 분석 비교군 보완

“리셋 후 새 응답을 받은 모델”과 “과거 모델을 동결한 모델”만 비교하면 새 응답의 효과와 리셋의 효과가 섞인다는 지적을 채택했다. **동일한 새 비교·응답을 과거 사후분포에 이어 붙이는 arm**을 추가했다. 0/8/24개 모두 사용자별 짝 차이와 bootstrap 구간, 개선/동률/악화 수를 [결과](../artifacts/simulation.ko.md)에 보고한다.

이 arm은 v2 결과를 본 뒤 추가했으므로 별도의 탐색적 보완이다. 구간에 0이 있다는 것을 동등성이나 비열등성 증명으로 해석하지 않는다. 여러 상황과 checkpoint를 보았기 때문에 확증적 유의성 주장도 하지 않는다.

## 검증 범위와 남은 일

로컬 회귀 테스트 26개가 통과했다. 학습 모듈·epoch 포인터·저장소 재개방·동일 응답 비교 실험까지 확인했다. 실제 서비스의 모든 질문·피드백을 원자적으로 저장하는 API, 로그인 인증, 영구 감사 운영, 실제 사용자 검증, UI·구매 실행 연동은 완료했다고 주장하지 않는다. Grok의 동의는 독립 실행 검증이 아니다.

## 결과 전달 확인

`GROK-LEARNING-R2-CLOSE`로 검증 결과를 전달했다. Grok는 E1을 기존 버그가 아닌 회귀 테스트 보강으로 정정했고, E2와 동일 응답 비교 결과를 다음 검토의 기준선으로 수신했다. 답변의 `verified_in_code` 표현은 우리가 보낸 실행 결과에 대한 판단이며 Grok가 직접 파일을 읽거나 테스트를 실행했다는 뜻은 아니다. 새 변경이나 재현 가능한 반례가 있을 때 검토를 이어간다.
