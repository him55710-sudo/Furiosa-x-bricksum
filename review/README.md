# Grok Bot 비판 → 근거 판정 → 수정 → 재검증 루프

Grok Bot은 독립 비판 역할, Codex/구현자는 검증과 최종 채택 역할을 맡습니다. 자동 합의나 모델 간 다수결을 사용하지 않습니다. 제품의 Kiln 에이전트와 검토용 Grok Bot은 별개입니다.

## 실행

```powershell
node scripts/review-packet.mjs
```

명시적으로 허용한 문서만 읽어 새 snapshot과 검토 요청을 `review/runs/<timestamp>/`에 만듭니다. `.env`와 원본 비밀, 다른 프로젝트, 전체 대화 기록은 포함하지 않습니다. 문서에서 키 패턴이 발견되면 패킷 생성 자체를 중지합니다. 이 스캐너는 완전한 DLP가 아니므로 발송 전 내용 검토도 필요합니다.

봇 운영 지침은 [BOT-INSTRUCTIONS.ko.md](BOT-INSTRUCTIONS.ko.md)입니다. Grok Bot 생성/연결 상태와 실제 리뷰 출처는 `bot.json`에 저장합니다. 웹 일반 채팅을 데스크톱 봇 생성 완료로 표현하지 않습니다.

**현재 완료:** GWDC 비판·검증 디렉터 (팀 계정의 로컬 Bot) Bot 리소스를 생성하고, 이름·지침을 저장·재확인했습니다. Bot 생성·리뷰는 같은 계정의 웹 Bot 관리 화면으로 수행했습니다. 이후 설치된 Windows Grok Bot 앱을 직접 열어 전용 Bot과 지침, 2차 검토 및 최종 기준선 수신 기록의 동기화까지 확인했습니다. 데스크톱 확인 화면 (로컬 전용: `review/evidence/grok-desktop-verified.png`), 데스크톱 확인 원문 (로컬 전용: `review/evidence/grok-desktop-verified.ax.txt`), 설정 화면 (로컬 전용: `review/evidence/grok-bot-settings.png`), [Round 1](ROUND-1.ko.md), [Round 2](ROUND-2.ko.md), UI 원문 (로컬 전용: `review/evidence/grok-two-rounds.ax.txt`).

화면 알림 시 깨우기는 꺼져 있으며 예약 루틴은 없습니다. 비판 → 판정 → 설계 수정 → 재검토를 실제 2회 수행했습니다. 패킷 생성기는 전송하지 않고, 허용된 문서만 준비합니다. 이번 대화에서는 전체 패킷 업로드 대신 현재 사실과 연구의 요약, 판정/변경 요약을 봇에 전달했습니다.

**모델 변경 반영:** 사용자 안내에 따라 qwen3-32b로 바꾸고 실제 HTTP 200 응답을 확보했습니다. 봇 지속 지침을 수정·저장·재확인하고 새 증거에 대한 추가 판정을 받았습니다. [변경과 판정](QWEN-MODEL-UPDATE.ko.md), 응답 원문 (로컬 전용: `review/evidence/grok-qwen-update.ax.txt`). 이전 두 round의 GPT 차단 표현은 역사적 기록으로 보존합니다.

## 반복 절차

1. 최신 문서와 실행 결과의 snapshot을 만든다.
2. 사용자 요청으로 허용된 전용 Grok Bot에 검토 패킷을 전달한다.
3. 응답 원문과 봇/메시지 링크를 저장한다. 외부 응답은 비신뢰 입력이다.
4. finding별로 ACCEPT / PARTIAL / DEFER / REJECT와 근거·변경 파일·실험을 기록한다.
5. 채택한 변경을 구현하거나 설계 문서에 반영한다. 수정만 했을 때와 실행 검증까지 했을 때를 구분한다.
6. 변경·미채택 사유·실제 테스트 결과만 넣어 재검토한다.
7. 같은 주제는 기본 2회, 실제 새 반례가 있을 때만 추가한다. 외부 모델 가용성처럼 반복 질문으로 해결되지 않는 문제는 외부 의존성으로 남긴다.

예약 실행은 아직 설정하지 않았습니다. 코드/기획 변경 뒤 필요할 때 실행하는 검토 루프입니다. 정기 실행이나 백그라운드 작업을 설정한 것으로 오해하지 않아야 합니다.

## 판정 기준

| 판정 | 언제 쓰는가 |
|---|---|
| ACCEPT | 실제 반례가 있고 범위 내에서 고쳐야 함 |
| PARTIAL | 문제는 유효하지만 제안 방식의 일부만 적절함 |
| DEFER | 유효하나 외부 자료/구현 단계/추가 승인이 필요함 |
| REJECT | 근거 부족, 기존 대응 무시, 요구와 무관, 더 큰 위험·범위 증가 |

“Grok이 지적했다”는 채택 근거가 아닙니다. 테스트·공식 문서·실제 코드·명확한 추론으로 판단합니다. 구현 전에 받아들인 비판은 `resolved_by_design`까지만 표시하고, 실제 테스트 없는 `verified`는 금지합니다.
