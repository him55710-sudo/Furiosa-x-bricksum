# Grok Bot Round 1 — 수신 비판과 판정

수신일: 2026-09-28. 원문 봇 대화 (팀 계정의 로컬 Bot). 아래는 UI에서 읽은 응답의 요약이며 원문 전문 전사가 아닙니다. 외부 비판을 사실로 자동 승격하지 않습니다.

| ID | Grok 비판 | 판정 | 수용 또는 기각 이유 | 다음 증거 |
|---|---|---|---|---|
| R1-01 | 필수 모델 부재; 모델 어댑터와 대체 리허설 필요 | PARTIAL | 가용성 차단 수용. 모델 부재가 ‘0점’이라는 단정은 채점표 근거 없어 기각. 다른 모델의 리허설은 요구 충족 증거와 분리 | 필수 모델 live response와 운영사 라우팅 근거 |
| R1-02 | 항상 총액 사전 검사하는 단순 비교군보다 나은가 | ACCEPT | 가장 강한 반례. 3-arm 비교와 무효 가설 추가. 기억이 무익하면 주장 축소 | B0/B1/CM 비용·효용·과잉차단 실험 |
| R1-03 | 동일 사건을 학습/평가에 재사용하여 편향 | PARTIAL | 사전등록·holdout·반복·분산 수용. Kiln seed/temperature 결정성은 미확인. 다른 merchant는 memory scope 밖이므로 일반화 성능과 혼동 금지 | 같은 scope의 새 견적 holdout + scope 밖 음성 대조 |
| R1-04 | 오래된 규칙이 정상 구매/협상을 막음 | PARTIAL | 순서 통제·정상 개선·과잉차단 집계 수용. 자동 만료로 통제를 조용히 제거하는 방식은 기각. 현재 승인 한도로 판단하고 해제는 승인된 lifecycle로 처리 | 개선된 견적·협상 가능·버전 변경 테스트 |
| R1-05 | 다른 층에서 차단되는 증거 부족; testnet revert 필수 | PARTIAL | 독립 위반 run과 contract 우회 테스트 수용. testnet revert가 대회 필수라는 주장은 기각. production 검사 끄기 기능은 만들지 않음 | 격리 contract harness + 정상 성공 tx |
| R1-06 | 시뮬레이터 서명으로 실제 판매자 신뢰를 입증 못함 | PARTIAL | 서로 다른 seller key와 고정 manifest, 신뢰 가정 수용. 별도 프로세스 자체가 독립 신뢰를 보장하지는 않음 | 서명 후 변조 실패, signer manifest 승인 결합 |
| R1-07 | 허용 범위 안의 나쁜 선택/주입은 남음 | PARTIAL | 적격성과 정상 효용 평가 수용. 무조건 최저가는 환불 선호를 무시하므로 기각. 하드 조건은 코드, 선호는 승인된 목적과 성과 지표로 평가 | SKU/최소 수량/환불 하한 + 공격/정상 쌍 |
| R1-08 | 중지/UNKNOWN은 아직 계획; 재시도 위험 | ACCEPT with correction | 경합·복구 테스트 수용. ‘더 높은 nonce로 대체되면 예약 해제’는 틀림. replacement는 같은 nonce이며 효과 확인 전 해제 금지 | 같은 nonce의 거래 효과·paymentKey·receipt 대조 |

Grok이 제안한 제외 범위(공유 평판, CaMeL 인터프리터 자체 구현, 멀티체인/실제 자산 확장)는 유지합니다. 위 판정은 제품 구현 완료를 뜻하지 않습니다.

## 새 실험 기준

- B0: memory 없이 최종 결제 전 동일한 안전 검사.
- B1: 모든 후보에 항상 확정 총액을 먼저 요구하는 단순 기준선.
- CM: 검증된 사건의 범위에만 더 이른 확정 총액 요구.
- 공통: 같은 최종 예산·수취인·기한·서명 검사, 같은 견적 원본, 같은 승인 목적.
- 측정: input/output tokens, quote API 횟수·지연, 성공률, 구매 가격/조건, 과잉차단, 재승인 요청, 통제 유지 비용.
- 반증: B1이 모든 사전등록 시나리오에서 CM보다 같거나 우수하면 효율성 차별화 주장을 철회. 조건부 이득만 있으면 조건을 명시.

## 협상과 최종 결제의 구분

‘총액을 먼저 공개하라’는 ‘현재 호가가 예산보다 높으면 협상을 영구 금지하라’와 다릅니다. 공개 비용을 알고 예산 안으로 낮추는 협상은 사전 승인된 추론/라운드 예산 안에서 가능합니다. 최종 견적이 예산을 넘으면 결제는 반드시 차단합니다. 확정 견적 자체가 협상 후에만 가능한 판매자는 명시적 REVIEW_REQUIRED 또는 거절로 끝내며 무한 루프를 만들지 않습니다. 이 tradeoff도 실험에 포함합니다.
