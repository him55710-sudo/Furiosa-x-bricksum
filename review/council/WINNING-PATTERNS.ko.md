# 수상 사례에서 가져올 검증 가설

2026-09-28 확인. 목적은 다른 팀의 기능을 복제하는 것이 아니라 우리 작업의 가치와 증거를 개선하는 것이다. 아래는 의도적으로 고른 작은 표본이다. 탈락작 대조·전체 출품작 분석·심사위원별 점수가 없으므로 수상 원인이나 우승 확률을 추정하지 않는다. 종합 우승·부문 수상·결선 진출을 구별한다. 사례 설명은 주최 측 발표 또는 출품자 설명이며 이 세션이 타 제품을 직접 실행한 결과는 아니다.

## 프로젝트에 적용할 패턴

다음은 자료를 바탕으로 한 **검토자의 추론**이다. 각 행을 우리 프로젝트의 실제 증거로 확인한다. 모든 수상작이 모든 항목을 충족한다는 뜻은 아니다.

| ID | 패턴과 출처 | Control Memory의 확인 질문 | 최소 관측·반증 |
|---|---|---|---|
| WP1 | 한 사용자·한 작업 (W03,W05) | 예산 책임자가 PDF→CSV 한 건을 맡기는 이유가 설명되는가? | 실제 최근 업무/대안 확인. 반복 문제가 없으면 수요 가설을 낮춤 |
| WP2 | 받은 결과가 보임 (W01,W02,W03) | ‘승인 8 → 청구12 차단 → 정상6 → 파일 수령’이 실행되는가? | 같은 작업 ID의 입력·지급·CSV·검사 결과. 지급만 있으면 업무 완료 아님 |
| WP3 | 지정 기술이 결과를 바꿈 (W03,W04,W05) | Qwen의 조건 해석, 계약의 권한 집행이 각각 필요한가? | 규칙 기준선과 해석 품질 비교, 백엔드 우회 시 계약 거부. 차이 없으면 해당 AI 경로 단순화 |
| WP4 | 심사자가 재구성할 자료 (W04 + 제출 지침) | 원 서버 없이 승인·거래·파일 일치를 설명할 수 있는가? | 고정 버전·증빙·검증 명령, 원본/변조/누락 판정. 링크 존재만으로 재현 성공 판정 금지 |
| WP5 | 핵심 기능만 시험·개선 (W01 인터뷰) | 다음 변경 하나가 어떤 불확실성을 줄이는가? | 변경 전 가설·현재값·완료 조건, 변경 후 같은 조건의 결과. 기능 개수는 성과 아님 |
| WP6 | 짧고 이해되는 시연 (W01 + 데모 지침) | 처음 본 사람이 한도·지급·결과를 구분하는가? | 기존 3명 사용성 계획의 시간·오답·도움 기록. AI 역할극은 인간 관찰로 세지 않음 |

보완 지침: [Devpost의 데모 안내](https://info.devpost.com/blog/6-tips-for-making-a-hackathon-demo-video)는 실제 실행을 보여주고 문제·해결·구현을 짧게 설명하도록 권한다. 이 행사에 다른 대회의 영상 길이나 심사 배점을 적용하지 않는다. 현재 4분 대본은 내부 목표이며 실제 제출 제한은 해당 대회 원문을 따른다.

## 무엇을 배우지 않을 것인가

토큰 발행·다중 에이전트·새 체인·복잡한 UI가 수상을 만든다고 추정하지 않는다. 공개 테스트넷 선택을 원래 devnet 허용 기준보다 상위의 필수 규칙으로 바꾸지 않는다. 멋진 결과 영상으로 미구현 기능을 대체하지 않는다. 고객·수익·전력 절감·정확도를 창작하지 않는다.

사례를 추가할 때 행사/연도/정확한 상격/원문/관측/추론/우리의 반증 조건을 남긴다. 유의미한 완료 회차 5개 이후 또는 공식 규칙 변경 때만 필요성을 검토하고, 실제 빈칸이 있을 때 공식 자료 1~2건으로 보완한다. 새 사례가 현재 문제를 바꾸지 않으면 개발 우선순위를 바꾸지 않는다.
