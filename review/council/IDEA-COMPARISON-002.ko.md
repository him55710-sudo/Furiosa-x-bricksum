## 다음 실험 EV-007: 상품과 판정 경계를 먼저 검증

**가설:** 회사 리서치용 데이터 납품 한 건에서, 협상한 객관적 납품 조건과 escrow 전이를 연결하면 구매·판매·감사의 역할이 한 장면으로 설명된다. 다만 신뢰 주체·추가 구현량이 v3보다 커질 수 있으므로 아직 더 좋은 제품이라고 확정하지 않는다. WP1/2/3/4/5/6을 이 가설에 적용하며 우승 확률은 계산하지 않는다.

첫 후보는 **팀 운영 판매자에게 요청한 특정 버전의 데이터 묶음 한 건**이다. 구매자는 필요한 컬럼·기간 범위·자료 출처·검사 규칙을 지정하고 판매자는 가격·제공 범위·기한을 제안한다. 이는 시장 검증된 상품이 아니라 최소 설계 후보다. 행 수만 늘린 가짜 데이터가 통과하거나 구매자가 유용성을 판단할 방법이 없으면 이 후보를 기각하고 더 객관적인 산출물로 좁힌다. ‘데이터를 샀다’는 장면을 만들기 위해 의미 없는 거래를 강제하지 않는다.

최소 산출물은 제품 구현이 아니라 **합의 schema 한 개 + 자금 상태표 + 고정 반례**다. `purchaseId, input/resourceSpecHash, deliverableSpecHash, validatorVersion, buyer, seller, asset, price, deadline, settlementAuthority`를 같은 서명된 합의에 묶는다. 대화 hash는 합의의 배경 증거이며 대화 내용만으로 지급 권한이 생기지 않는다. 회사 mandate의 범위 밖 조건을 AI가 새로 승인하지 않는다.

세 가지 역할을 분리한다.

- Buyer/Seller: 목적과 조건을 제안하고 확인한다. Qwen이 선택한 결과·근거와 정형 정책을 구별한다. 판매자 mock은 명시하고 여러 유료 모델 호출을 자동으로 추가하지 않는다.
- 검증 코드/판정자: bytes·schema·명시된 조건을 확인한다. 계약은 오프체인 HTTP 결과를 저절로 알지 못한다. 승인된 attestor 서명, 당사자 승인, 또는 계약이 직접 검증할 증명 중 한 방식을 명시해야 한다. 단일 운영자 attestor라면 그 신뢰를 공개한다.
- 감사 보고: 검증된 증빙을 읽고 승인·합의·예치·수령·정산/환불을 설명한다. 감사 LLM은 release 권한이 없고, 설명의 근거가 없는 부분은 미확인으로 남긴다.

`LOCKED → RELEASED`와 `LOCKED → REFUNDED`는 한 거래에서 둘 다 일어나면 안 된다. 정상 release, 빈/불일치 납품, 무가치하지만 schema 통과 데이터, 중복 release, 판정자 미응답, 기한 경계의 release/refund 경합을 표에 넣는다. 만료 환불도 누군가 거래를 제출해야 하며 가스·제출 주체와 실패 시 상태를 적는다. timeout 후 무조건 buyer 환불은 이미 전달한 seller를 해칠 수 있다. 판정자가 중단되거나 악의적일 때의 손실을 숨기지 않는다. 납품 증명과 결과 접근 권한도 별개다.

**완료:** 상품 하나·구매자 한 업무·검증 입력·판정권자·release/refund 표·고정 정상/반례·범위에서 뺀 항목을 기획 v3의 후속 결정에 연결한다. 전이 검사는 오프라인에서 시작할 수 있다. 실제 체인 escrow와 Qwen 협상은 구현·실행 후에만 완료로 표시한다.

**기각/보류:** row/hash만으로 품질을 보장한다고 주장하거나, 합의를 만드는 것보다 판정자·판매자 도입 부담이 커지고 그 필요의 근거가 없으면 자동 escrow 제품 주장을 축소한다. v3의 지급/수령 분리·purchaseId·복구는 재사용 가능한 안전 설계로 남긴다.

## 우승을 막을 수 있는 구체적 약점

1. **새 UI 아래에 판정자가 숨음:** 중앙 서버가 ‘성공’을 말하면 계약이 지급하는 구조에서, 계약이 실제 품질을 검증했다고 발표하면 반례 하나로 무너진다. 판정자의 권한과 한계를 데모에 드러낸다.
2. **추가 구성요소가 사용자 문제보다 큼:** SDK+DB로 충분한 고객에게 escrow·판매자 동의·새 계약을 요구할 수 있다. 아직 인터뷰/채택 근거는 없으며 공개 API 존재로 대신하지 않는다.
3. **AI/협상이 장식이 됨:** 고정 데이터·고정 가격이면 조건 협상에 모델이 필요한지 약하다. 애매한 요구를 검증 가능한 합의로 바꾸는 실제 유용한 단계와 코드 기준선을 정한다.
4. **데모 범위 증가:** 정상 납품·반례·서버 밖 증빙 하나가 연결되기 전에는 회사 플랫폼, 여러 상품, 추가 통제 학습을 늘리지 않는다. escrow·refund를 애니메이션만으로 구현 완료로 표시하지 않는다.

## 확인한 외부 자료와 주장 범위

2026-09-28 [x402 exact EVM 공식 명세](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_evm.md)는 서명에 따른 정확한 금액·목적지의 전송과 pending settlement 처리를 설명한다. [payment-identifier 명세](https://raw.githubusercontent.com/x402-foundation/x402/main/specs/extensions/payment_identifier.md)는 요청 binding·같은 요청의 응답 재사용을 이미 다룬다. 따라서 v3의 기존 SDK 인정은 적절하다. **우리의 납품 조건 escrow가 표준 exact 판매자에 바로 호환된다는 결론은 이 자료에서 나오지 않는다.** 판매자가 해당 계약/판정 방식을 수락해야 하며 현 MVP에는 아직 그런 통합 증거가 없다.

예시 가격·500/624 rows·100회·에너지 절감·우승 가능성은 관측값으로 채택하지 않는다. 제3자 재구성은 기존 핵심 요구로 유지하며, Qwen/NPU의 연동·실측 토큰과 하드웨어 에너지 계측은 구별한다.
