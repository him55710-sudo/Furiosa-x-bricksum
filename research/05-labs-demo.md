# 학습 실습과 해커톤 증거 준비

아래는 실행할 작업과 통과 기준이다. 체크되지 않은 항목을 완료·실측으로 발표하지 않는다. 시간은 학습 계획용 가정이며 API·faucet·계정 상황에 따라 달라진다.

## 1회차 · 개념과 API (약 1~2시간)

1. [기초 문서](01-foundations.md)를 읽고 AI/코드/체인의 역할을 말로 설명한다.
2. 대회 계정의 모델 목록과 지정 모델 호출을 확인한다. 기획 세션에서 만든 연결 검사 스크립트가 있다면 그것을 사용한다.
3. 정상 응답의 `model`, `finish_reason`, `usage`, 요청 식별자를 기록한다.
4. tool calling이 있으면 이름과 인자를 검증하고, 잘못된 출력은 실행하지 않는 흐름을 만든다.

**통과 기준:** “AI가 무슨 일을 했는지”와 “실행을 허용한 코드는 무엇인지”를 분리해 설명할 수 있다. 모델이 없으면 `BLOCKED_MODEL_UNAVAILABLE`로 남기고 다음 독립 실습을 진행한다. 임의의 대체 모델 결과를 대회 증거로 사용하지 않는다.

## 2회차 · 정책과 원장 (약 2~3시간)

설명용 예산 100, 상품 총액 70 두 건을 동시에 시도해 본다. 둘 다 통과하면 버그다. 검사·예약을 원자적으로 처리하고, 재시도에도 예약이 중복 생성되지 않게 한다.

**통과 기준:** `settled + reserved <= budget`이 유지되고, 거절도 사유가 있는 이력으로 남는다. 금액은 최소 단위 정수다.

Control Memory 첫 사례는 “수수료로 거절된 판매자에게 다음에는 확정 총액 견적을 먼저 요구”하는 규칙으로 제한한다. 적용 범위를 판매자·상품·자산과 연결하고, 견적 만료와 정책 버전을 확인한다. 판매자 텍스트를 규칙으로 저장하지 않는다. 변경된 금액·정책을 무시하는 영구 차단 캐시는 만들지 않는다.

## 3회차 · 체인과 검증 (약 2~3시간)

1. 기획에서 정한 devnet/testnet과 chain ID를 확인한다.
2. 최소 기능을 실행해 거래 hash와 receipt를 얻는다.
3. 로그의 `execution_id`를 이벤트 또는 기록 hash와 연결한다.
4. 원본 승인 묶음을 다른 검증자가 읽고 승인·정책·실행을 재검사하게 한다.
5. bundle 사본의 금액을 바꾸어 검증이 실패하는지 확인한다.

**통과 기준:** 블록 탐색기 링크만 보여주는 것을 넘어서, 실제 결과가 어떤 승인과 연결됐는지 재현할 수 있다. 기록만 온체인이면 그 범위를 명시한다.

## 4회차 · 효율과 발표 (약 1~2시간)

핵심 실험은 동일한 최종 안전 검사를 가진 A(통제 기억 없음)와 B(통제 기억으로 더 일찍 검사)를 비교한다. 제품이 달라지거나 사용자 목표가 바뀌지 않도록 같은 fixture·정책·모델을 사용한다. 문맥 요약 최적화는 별도 실험으로 두어 무엇이 영향을 주었는지 구분한다. 각 조건을 여러 번 반복하고 시도별 로그를 남긴다. 해커톤 탐색 실험으로 조건당 5회 이상을 시작점으로 삼을 수 있지만 충분한 통계 검증을 뜻하지 않는다.

**통과 기준:** 정상 업무 성공률, 위반 차단 결과, 호출 수, 입출력 토큰, 지연을 함께 공개한다. 실패 실행·재시도도 포함한다. 장치 계측이 없으면 “토큰 절감 실측, 전력 절감 미측정”으로 구분한다.

## 반드시 준비할 테스트 표

아래 값은 **fixture용 가정**이다. 테스트를 실행했다는 뜻이 아니다.

| ID | 시나리오 | 예상 결과 | 남길 증거 |
|---|---|---|---|
| T01 | 허용 판매자, 예산 안, 유효 기한 | 정상 실행 | 승인 → 실제 Kiln 응답 → 정책 검사 → tx/receipt |
| T02 | 상품 95 + 판매자 수수료 10, 예산 100 | 제출 전 차단 | `BUDGET_WITH_FEES`, 계산 입력, 실행 미발생 |
| T03 | 목록 밖 수신 주소 | 제출 전 차단 | `MERCHANT_NOT_ALLOWED` |
| T04 | 위임 기한 만료 | 제출 전 차단 | `MANDATE_EXPIRED` |
| T05 | 예약 후 제출 전 사용자 중지 | 새 제출 차단·예약 정리 | 중지와 제출 상태의 순서 |
| T06 | 예산 100에 70 두 건 동시 요청 | 둘 다 지출하지 않음 | 잠금·예약·결정 이력 |
| T07 | 같은 구매 요청 재전송 | 경제적 효과 최대 1회 | idempotency key, execution ID, 체인 결과 |
| T08 | 판매자 텍스트의 권한 확대 지시 | 정책 불변 | 공격 입력, 거절 또는 허용 범위 내 결과 |
| T09 | 승인 후 금액/주소/견적 변경 | 재승인 필요 또는 차단 | proposal hash 불일치 |
| T10 | RPC 전송 timeout | 결과 불명 추적, 새 지급 금지 | nonce/tx hash와 reconciliation |
| T11 | 영수증 bundle의 금액 변조 | 검증 실패 | 원본·변조본 hash 및 verifier 결과 |
| T12 | API 오류·불완전 JSON·출력 잘림 | 자동 지출 없음 | 모델 오류와 제한된 재시도 이력 |

T02·T03은 대회에서 요구한 최소 2회 경계 위반 시연의 중심이다. 나머지는 백엔드가 실제로 우회·경쟁 조건을 다루는지 확인하는 추가 항목이다. 거절된 시나리오에 결제 tx가 생겼다면 사후 실패 표시만으로 성공한 차단으로 세지 않는다.

## 대회 조건과 제출 증거 매핑

| 기준 | 보여줄 것 | 자료 폴더에 남길 것 |
|---|---|---|
| Declared Function & User Need | 사용자와 문제를 한 문장으로 선언 | README, 입력→결과 시나리오 |
| Boundaries & Stopping | 실제 enforcement 지점과 2회 이상 차단 | reason code, 정책 버전, 로그 |
| Kiln & Efficiency | 지정 모델 실제 호출이 후보 선택에 쓰임 | 단계별 요청 ID·usage, 비교 보고서 |
| Blockchain | devnet/testnet의 실제 결제/정산/기록 | chain ID, contract, tx hash, receipt, 연결 로그 |
| Approval & Evidence | 예산 부여·조회·중지·영수증·제3자 재구성 | 서명/승인, 정책 snapshot, 검증 결과 |

대회 기준의 출처는 기획 채팅에 사용자가 제공한 Challenge B 본문이다. 이 조사에서 주최자의 최신 별도 규칙 페이지까지 검증한 것은 아니다.

## 측정용 CSV 헤더

```csv
run_id,variant,scenario_id,attempt,flow,model,generation_id,prompt_tokens,completion_tokens,total_tokens,cached_tokens,reasoning_tokens,cost_usd,latency_ms,outcome,usage_status,energy_j,energy_method
```

결측은 빈값과 `usage_status=missing` 등으로 표시한다. 숫자 0은 실제 0으로 확인한 경우에만 쓴다. 카드 전력·서버 전력·전체 서비스 전력의 측정 범위를 구분한다. 지연 평균 하나보다 median과 tail latency를 함께 보되 적은 표본의 p95를 과신하지 않는다.

## 데모 리허설 순서

1. 승인 화면에서 예산·수신처·기한·수수료 부담을 보여준다.
2. 정상 실행에서 AI가 선택한 견적과 코드의 검사 결과를 연결한다.
3. 수수료 초과와 비허용 판매처를 차단하고 그 이력을 보여준다.
4. 중지를 누른 이후 새로운 실행이 시작되지 않는 것을 보여준다.
5. 거래 hash와 영수증 묶음을 다른 화면/검증기로 재확인한다.
6. 단계별 토큰 표와 최적화 전후 비교를 보여준다.

소스 코드, fixture, 사용량, 체인 receipt와 검증 출력의 버전을 맞춘다. 정상 흐름만 녹화한 영상으로 경계 조건을 대체하지 않는다.
