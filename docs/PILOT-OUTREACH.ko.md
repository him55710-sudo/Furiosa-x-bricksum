# 후보별 연락 초안 — 미발송

2026-09-29. 발신자의 실명·소속·회신 경로는 실제 발송 계정에서 표시한다. 외부 게시·메일 전송·회원 가입은 수행하지 않았다. 공개 이슈에는 비밀 자료나 개인 연락처를 올리도록 요청하지 않는다. 커뮤니티 글은 운영 규칙에 맞는 모집 공간에서만 사용한다.

## 1. FinRobot / AI4Finance: 최근 실제 업무 사건 인터뷰

경로: [공식 사이트](https://ai4finance.org/)가 연결하는 [커뮤니티](https://discord.gg/trsr8SXpW5). 특정 신고자의 이슈에 홍보 답글을 달지 않는다.

**Subject: 15-minute research interview: failed financial-data jobs and retries**

Hello, we are building a hackathon prototype for verifying outsourced financial-data deliverables before releasing test payments. We are looking for a developer who has recently handled a failed or incorrect data job in a research workflow.

FinRobot's public issue #113 describes a data-collection failure after retries. We have not reproduced that incident and do not assume it involved a billing loss. We would like to understand one real workflow: what was requested, what failed, how it was checked, and whether the existing provider's retry/refund process was sufficient.

Would you be willing to share your experience in a 15-minute conversation? No API keys, client documents, wallet connection, or payment are needed. A public example or a summary with identifying details removed is enough. If you have not had a paid-work problem, that is useful feedback too. Please reply with whether this fits your experience and your preferred next step; do not post private documents here.

## 2. Inn Corp: 납품 검사·부분 실패 과금 질문

경로: [Actor Issues](https://apify.com/inn_corp/pdf-text-table-extractor/issues/open). 개발자 소개가 질문·요청 경로로 안내한다.

**Subject: Financial-table acceptance criteria and partial-output billing**

Hello, your PDF extractor documents separate page/table outputs, scanned-page handling, and failure-aware billing. We are evaluating a public financial-report task that needs the correct period, row, unit, sign, and source evidence, rather than only a successfully processed PDF.

For a document that produces output but extracts the wrong row or incomplete quarters, can an agreed acceptance check be applied before the work is considered successfully delivered? Does your existing support/billing process already resolve that case?

We have a small public task packet and a testnet-only prototype. If this is relevant, would you be open to reviewing one task and explaining acceptable delivery/rework terms? We have not run or purchased your Actor and are not asking you to connect a wallet. We would agree scope and costs separately before any pilot work.

## 3. ootssu: 기존 정형 API로 충분한지 확인

경로: [재무제표 Actor Issues](https://apify.com/ootssu/korea-company-financials/issues/open).

**제목: 공시의 분기 시설투자 수치와 출처 확인에 관한 기능 문의**

안녕하세요. 공개 재무자료에서 기간·행·단위·부호를 확인한 뒤 결과를 전달하는 해커톤 프로토타입을 만들고 있습니다. DART 기반 정형 데이터를 제공하시는 Actor를 확인했습니다.

예를 들어 LG에너지솔루션 2026년 2분기 실적 PDF에 실린 2025년 네 분기의 시설투자 현금유출을 각각 확인하려 할 때, 현재 API의 분기/누적 구분과 계정 식별자로 같은 결과를 충분히 얻을 수 있는지 궁금합니다. 원문에서 어느 기간·행을 확인했는지도 추적할 수 있는지 알고 싶습니다.

기존 API로 해결된다면 별도 PDF 외주나 에스크로를 추가할 이유가 없다고 보고 있습니다. 지원 범위와 아직 수작업 검토가 필요한 경우를 알려주실 수 있을까요? 실제 고객 자료나 계정 정보는 요청하지 않으며, 현재 서비스 이용·결제·파일럿 계약은 진행하지 않았습니다.

## 4. Upstage: 문서 검수 경험과 기술 의견 요청

경로: [공식 Document Parse 문의](https://www.upstage.ai/contact-us/document-parse), `contact@upstage.ai`.

**제목: 공개 재무문서의 납품 검수 기준에 관한 짧은 의견 요청**

안녕하세요. 외부 작업자가 전달한 재무자료를 원문과 대조하고, 합의한 조건을 통과한 결과에만 테스트 대금을 지급하는 해커톤 프로토타입을 만들고 있습니다.

현재는 공개 실적 PDF의 네 분기 값과 기간·행·단위·부호·출처를 확인하는 작은 범위입니다. 문서 처리가 성공했더라도 다른 행을 읽거나 일부 분기만 제공한 경우를 실제 사용자가 어떻게 검수하고 재요청하는지 확인하고 싶습니다.

Document Parse의 현재 기능으로 충분히 해결되는 부분과 추가 수작업이 남는 부분에 관해 15분 정도 기술 의견을 주실 수 있을까요? 공개 문서만 사용하고 고객의 비공개 원문·API 키는 요청하지 않습니다. 제품 구매나 제휴가 확정된 요청은 아니며, 별도 비용이 발생하는 검토는 사전에 범위를 협의하겠습니다.

## 5. Apify 커뮤니티: 실무자 및 초면 검토자 모집

경로: [공식 개발자 포럼](https://discord.apify.com/). 모집 허용 공간을 먼저 확인한다.

**Subject: Feedback request: checking financial-data delivery and failed jobs**

We are testing a hackathon prototype that checks a data deliverable before releasing a test payment and records failed-job recovery. We would value feedback from people who have used or built paid document/data automation.

There are two optional ways to help: watch a 2-minute-37-second recorded demo and explain what you understood (about 5–10 minutes), or discuss one recent failed/incorrect data job and how you handled checks, retries, and billing (about 15 minutes). Prior knowledge of this project is not required for the demo test.

This is a prototype with simulated suppliers and testnet funds, not a live marketplace. No wallet, payment, private client documents, or API keys are required. We would record responses only with your agreement, under a participant code. Please indicate which option interests you; we will arrange the material and recording preferences before starting.

## 수락 답변을 받은 뒤 보낼 진행 안내

“감사합니다. 이번에는 [시연 이해도 / 원문 검토 / 최근 실제 사건] 중 동의하신 항목만 진행하겠습니다. 응답은 참가 코드로 기록하고 공개 발표 인용 여부는 별도로 확인합니다. 언제든 중단할 수 있고, 모르는 수치는 미측정으로 남깁니다. 영상 또는 공개 작업 자료를 전달한 뒤 진행하겠습니다.”

시연에는 최신 영상 파일을, 외부 QA에는 `artifacts/pilot-workpack/participant-kit.zip`만 전달한다. 시연 전 정답·대본을 읽히지 않고, QA의 평가자 정답 파일도 전달하지 않는다. 참가자 답변은 [접수 양식](PILOT-INTAKE.ko.md)과 [사람 검증 절차](USER-STUDY.ko.md)에 따라 기록한다. 응답 전 예약·동의·참가 완료를 대신 입력하지 않는다.
