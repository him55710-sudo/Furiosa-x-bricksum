# DealTrace — 구현 전 제품·증거 검토

2026-09-29. 최신 DealTrace 요청을 제품 이름과 범위의 기준으로 삼고, 이전 Agent Deal Assurance 지시의 좁은 고객·세 장면·기존 엔진 보존 원칙을 적용한다. 이 문서는 아래 후속 구현 전에 작성했다.

## A. 지금 실제로 있는 것

| 계층 | 구현·증거 | 현재 한계 |
|---|---|---|

## B. 이야기 충돌

1. README와 UI에 이전 제품·포트·여러 데모가 섞여 첫 사용자가 무엇을 봐야 할지 어렵다.
2. 정상 지급이 보조 사례다. 첫 협상은 바로 오류 납품으로 끝나므로 기본 성공 흐름이 약하다.
3. 단순 2.20 예산 초과는 있지만 “관리자가 증액했다”는 판매자 주장이 인간 위임과 충돌하는 장면은 없다.
4. 공개 체인 증거와 새 협상 계층의 증거가 따로 있다. 이전 tx로 새 계층까지 검증했다고 표현하면 안 된다.
5. 고정 PDF의 이미 알려진 네 숫자를 구매하는 이유가 약하다. 데모는 외부 접근·도구·처리 능력이 필요한 비동기 리서치 배치의 한 검수 단위로 설명한다. 실제 유료 수요는 미검증이다.
6. 합의 해시·정책 코드가 전면에 있고, 돈이 어디 있는지와 사용자가 얻은 결과는 눈에 잘 들어오지 않는다.

## C. 그대로 재사용

Mandate / Deal / Policy / immutable hashes / escrow / validator / receipt / buyer recovery / durable signed intents / Control Memory를 유지한다. 새 ledger를 통과해야 하는 위임은 기존 accept API로 우회할 수 없게 한 검사를 유지한다. 모델은 outward message와 의미 후보만 생성한다. 정산, 권한 확대, 통제 완화 도구를 추가하지 않는다.

## D. 메인에서 접을 것

메인에는 정상 협상·지급, 권한 조작 차단, 오납품 환불·재거래 제한 세 장면만 둔다. 저가 전망치 의미 충돌은 추가 검증으로 남긴다. 이전 purchase UI, 모든 복구 시연, 긴 회귀 목록, 기존 영상은 Historical Engineering Evidence로 접는다. 삭제하거나 과거 결과를 새 버전의 결과로 덮어쓰지 않는다. A2A/AP2/ERC-8183·기업용 RBAC·HSM·회계 연결은 미래 그림 한 장에만 둔다.

## E. 최소 변경 순서

1. 기존 정상/환불/예산/재거래 실행을 동일 회사·실제 순서의 세 장면으로 묶는다. 판매자 권한 주장을 메시지로 남기고 위임이 변하지 않는 회귀를 추가한다.
2. UI에 세 장면, 돈의 위치, 검수 결과, 원문 근거, 감사 영수증을 전면 배치한다. 기술 세부는 접는다. 저장 기록 재생과 새 실행을 구분한다.
3. 동일 협상 경로에 기존 Sepolia adapter를 연결하고, 영수증을 별도 RPC에서 재검증한다. 거래 대기/모호함에 새 거래를 만들지 않고 같은 저장 의도를 복구한다.
4. README를 요구된 열 개 항목과 하나의 Acceptance Matrix로 정리한다. 실제/시뮬레이션/미래를 명시한다.
5. 최종 소스에서 관련 회귀·전체 검사·브라우저 확인 후, 3분 발표 동선과 짧은 한국어 PDF를 갱신한다. 사람 이해도와 고객 수요는 실제 응답 없이는 완료라 하지 않는다.

## 구현 후 갱신

새 세 장면을 같은 회사·위임에 연결했고, 실제 Kiln 10회와 Sepolia 거래 4건으로 9/9를 통과했다. 가짜 관리자 증액 주장도 기록하면서 사람 상한이 변하지 않음을 검사했다. 새 협상·서명을 담은 공개 거래는 [별도 실증](DEALTRACE-PUBLIC-PROOF.ko.md)에 연결했다. README·네 화면·한 장 PDF·180초 한국어 영상은 이 실행을 중심으로 정리했다. A2A/AP2/ERC-8183나 기업용 운영 기능은 추가하지 않았다.

여전히 UNRESOLVED: 초면 사람의 감사 이해도, 외부 조직의 Agent 신원, 유료 외주의 실제 구매 수요, 미관측 자유 대화 성능, 하드웨어 전력 측정. 자동 검사나 작성된 가상 상황을 이 근거로 바꾸지 않는다.
