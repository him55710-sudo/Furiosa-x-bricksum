# Control Memory — 심사와 고객 검증을 연결한 개선 기획 v1

2026-09-28. [기존 아키텍처](ARCHITECTURE.ko.md)를 유지하는 실행 우선순위·발표·고객 검증 보완안이다. 구현 완료 선언이 아니다. 실제 제품 상태는 README와 실행 증거를 기준으로 판단한다.

## 제품 한 문장

**Control Memory는 팀 운영자가 AI에 맡긴 API 크레딧 구매의 승인 범위를 강제하고, 구매나 중지의 근거를 다른 사람이 다시 검증하도록 돕는 프로토타입이다.**

발표의 첫 질문: “이 구매는 누가, 어떤 조건으로 허락했나요?” 승인·견적·결과를 묶은 하나의 기록으로 답하고, 검증된 실패가 다음 시도의 검사 순서를 어떻게 바꾸는지 보여준다.

대표 사용자는 **이미 업무용 에이전트를 실험하며 유료 도구 예산까지 책임지는 소규모 팀의 개발 리드/운영자**로 좁힌다. 이는 인터뷰로 확인해야 할 가설이다. ‘모든 AI 사용자’나 ‘모든 기업’으로 확장하지 않는다. API 크레딧을 실제로 자주 구매하는지부터 확인하며, 빈도가 낮으면 이 사례의 상용화 가설을 재검토한다.

## 우리가 확인해야 할 문제

가설: 담당자가 수동 구매 승인과 공급자 영수증을 따로 관리하면 승인 조건·최종 수수료·실제 결과를 사후에 맞추기 어렵다. 에이전트의 설명만으로 승인 준수 여부를 판정할 수 없다.

아직 없는 증거: 실제 고객의 최근 사례, 수동 처리 시간, 발생 빈도, 실제 손실, 비용 지불 의사. 따라서 ‘검증된 시장 수요’, ‘감사 비용 X% 감소’, ‘시장 규모’, 매출 예측을 발표 사실로 사용하지 않는다.

제품 사용가치 가설은 두 개로 분리한다.

1. **기본 가치:** 승인한 한도를 지키며, 구매 또는 중지 결과를 재구성할 수 있다.
2. **추가 가치:** 검증된 실패에 따른 조기 검사로 불필요한 추론과 재작업이 줄어든다. 효과가 없더라도 기본 통제와 증거 기능의 결과는 독립적으로 평가한다.

## 대안 검토와 선택

| 접근 | 해커톤에서 증명할 내용 | 비용·한계 | 이번 선택 |
|---|---|---|---|
| 현재의 제한된 구매+BudgetVault+증빙 | 승인·AI 제안·통제·결제·재검증 연결 | 계약·원장·UI 통합 필요 | 유지. 한 개 정상 흐름부터 완성 |
| 외부 결제 후 증빙만 온체인 기록 | 이미 발생한 지출의 승인/기록 연결 | 지출 전 권한 강제의 책임 위치를 다시 정해야 함 | 현재 구현을 우회하는 대체안으로 몰래 전환하지 않음 |
| 실제 판매자·멀티체인 구매 플랫폼 | 넓은 업무 자동화 | 실제 상품 공급·계정·운영 문제까지 확대 | 후속 가설. 이번 MVP에 추가하지 않음 |

모의 판매자 세 곳, TestCredit, 단일 worker·SQLite, 선택한 한 체인이라는 기존 경계를 유지한다. 가짜 구매 영수증을 실제 상품 공급으로 표현하지 않는다.

## 구현 순서: 첫 관통 흐름 → 반례 → 차별점

일정과 팀 가용 시간이 확인되지 않아 시간 단위 추정이나 가짜 마감은 정하지 않는다. 각 단계는 완료 증거로 관리한다.

| 단계 | 이번에 만드는 결과 | 완료 조건 |
|---|---|---|
| 1. 구매 한 건의 전체 기록 | mandate/offer/run ID가 연결된 정상 요청, 결정론적 정책, 원장, export, 검증기 골격 | 오프라인 합성 입력으로 승인→결과 재구성. 합성임을 표시 |
| 2. 독립 통제 | 예산·수수료·판매자·기한·중지·예약·중복 통제와 계약 harness | 수수료 초과/비허용 판매자 STOPPED 2건; 경합·중복·변조 테스트 |
| 3. 실제 통합 | 같은 흐름에 qwen3-32b와 devnet/testnet 거래 연결 | 실제 모델 응답·flow usage, 성공 receipt와 matching run. 연결 진단은 성공, 제품·체인 통합은 미구현 |
| 4. 사람의 화면 | 승인·진행/중지·영수증/검증 결과 | 다른 사람이 설명 없이 결과·중지 사유를 찾음. 승인·중지 기능을 데모 장식으로 대체하지 않음 |
| 5. Control Memory | 기존 설계의 ‘더 이른 확정 총액 요구’ 한 종류 | source failure→control→다음 run의 검사 순서. B0/B1/CM 비용·품질 비교 |
| 6. 제출 | README 선언과 일치하는 4분 영상·증거 묶음 | 아래 acceptance 표의 실제 파일 경로와 run/tx ID가 채워짐 |

기존 [구현 인계](IMPLEMENTATION-HANDOFF.ko.md)의 안전 요구를 생략하지 않는다. 첫 흐름을 만들면서 각 모듈을 연결하고, 고급 화면 장식이나 추가 협상 전략보다 실제 결과를 우선한다. 외부 모델이 막혀도 1·2·4의 상당 부분을 진행할 수 있다.

## 심사 증거표

기준 출처: ‘기획 GWDC 챌린지 시스템 아키텍처’ 세션에 사용자가 제공한 Challenge B 원문. 공식 배점·마감·제출 링크는 별도 확인 대상이며 새로 만들어내지 않는다.

| Acceptance | 현재 판정 | 제출 때 반드시 연결할 증거 |
|---|---|---|
| Declared Function & User Need | 설계 문장 있음, 사용 가능한 결과 미구현 | README 선언→정상 run→사용자 영수증 |
| Boundaries & Stopping | 설계 있음, 제품 정책 미구현 | 독립 위반 2개 이상의 STOPPED와 결제 부재 확인 |
| Kiln & Efficiency | qwen3-32b 실제 후보 선택 1회 성공, 제품 흐름·에너지 증거 미완료 | 지정 모델 성공 응답이 제안에 쓰인 기록, flow별 usage, 에너지 측정/가정 구분 |
| Blockchain | 미구현 | 성공 tx hash/receipt·chain ID·contract·같은 run 이력 |
| Approval & Evidence | 설계 있음, UI/검증기 미구현 | 승인·관찰·중지·영수증, export만 받은 검토자의 재구성 |

2026-09-28 사용자 지시에 따라 필수 모델을 qwen3-32b로 변경했습니다. [실제 연결 진단](../artifacts/kiln/9292ce67-a174-406f-9021-f5e6a7dd8837.json)에서 HTTP 200, 후보 제안 검증, 760토큰을 확인했습니다. 자동 fallback이 아니며 이 단일 연결 진단을 제품 전체 acceptance 달성으로 세지 않습니다.

## 4분 발표 구성

- **0:00–0:25:** 담당자의 질문과 승인 조건. 30 TestCredit, 허용 판매자, 수수료, 기한을 화면에 표시한다.
- **0:25–1:15:** 정상 구매 한 건. 지정 Kiln 모델의 선택, 코드 검사, 테스트넷 결과, 영수증을 같은 run ID로 보여준다.
- **1:15–2:05:** 별도 run에서 수수료 초과와 비허용 판매자를 밀어 넣는다. STOPPED·이유·결제 부재를 제시한다. 사용자 중지 제어와 그 결과도 보여준다.
- **2:05–2:45:** 실패 기록에서 만들어진 통제와 재시도 순서를 비교한다. “효과가 있었는가”는 실제 호출·토큰·품질 값으로 말한다.
- **2:45–3:35:** 다른 사람이 export로 승인 준수를 재구성한다. 금액 변조는 INVALID, 자료 누락은 INCOMPLETE로 구별한다.
- **3:35–4:00:** 확인된 성과와 미확인 항목, 다음 고객 검증을 말한다.

이는 리허설용 시간 배분이다. 실제 통합이 없을 때는 준비 상태를 그대로 말하고 성공 영상을 연출하지 않는다. live 의존성 실패에 대비해 실제 실행 때 저장한 원본 기록·영상이 있으면 재생 사실을 표시해 사용한다.

## 차별점의 채택 조건

[기존 3-arm 프로토콜](EXPERIMENT-PROTOCOL.ko.md)을 바꾸거나 ‘모델이 반성했다’는 설명으로 대체하지 않는다.

- B0 비교·협상 후 최종 확정 견적/안전 검사 / B1 모든 후보에 조기 확정 견적 요구 후 최종 검사 / CM 사건이 있는 scope만 조기 견적 요구 후 최종 검사를 같은 조건에서 비교한다. 군 이름은 실험 프로토콜을 기준으로 한다.
- 정상 업무 성공, 과잉 차단, 사용자 개입, 견적 비용, 실패·재시도 포함 tokens/latency를 함께 본다.
- 차이가 없거나 CM이 불리하면 ‘추론 절감’ 주장을 철회한다. 승인과 통제 변경을 검증할 수 있다는 실제 구현 결과만 제시한다.
- 토큰 절약을 에너지 절약률로 환산하지 않는다. 에너지 계측/계수의 범위를 공개한다.

## 고객 검증 과제 — 아직 실행하지 않음

사용자가 연결할 수 있는 대상자 3명에게 최근 한 달의 실제 지출 위임 사례를 묻는 것을 제안한다. 자동 연락하지 않는다.

1. 가장 최근 AI/자동화 도구 지출을 누가 승인했고 결과는 어디서 확인했는가?
2. 수수료·범위·취소 문제를 마지막으로 겪은 때와 실제 대응은 무엇인가?
3. 지금도 작동하는 한도 설정·수동 구매·로그 방식으로 충분한 점은 무엇인가?
4. 준비된 증빙을 주고 도움 없이 구매의 승인 준수 여부를 판단하는 모습을 관찰한다.
5. 시험 도입을 원한다면 실제 제공할 샘플 자료와 다음 검증 날짜를 확인한다. 칭찬과 구매 약속을 구별한다.

기록 양식: 익명 참여자 ID / 역할 / 기존 흐름 / 사건 빈도 / 관측 시간 / 기존 도구 / 재구성 성공·오류 / 행동 약속 / 반증. 값은 관측 후 채운다. 3명은 초기 학습 표본이며 시장 검증 완료가 아니다.

상용화 가설은 ‘팀 단위 통제·증빙 도구’로 시작한다. 가격·수수료 모델은 검증 전 미정이다. 도입 마찰과 기존 도구 대비 효과가 없으면 기능 추가 대신 구매 사례 또는 제품 방향을 재검토한다.
