## 1. 제품 정의를 한 작업으로 고정

**제안 기능 문장:** “Control Memory는 소규모 팀의 문서처리 에이전트가 유료 PDF→CSV 작업을 맡을 때, 수수료를 포함한 사용자의 지출 한도를 강제하고 승인·결제·결과물 기록을 제3자가 대조하게 한다.”

현재 README의 구현 선언은 API 크레딧 구매다. 문서 변환 어댑터와 결과 수령이 실제 작동한 뒤에만 위 문장으로 바꾼다. 크레딧만 전송한 실행을 문서 변환 완료로 다시 이름 붙이지 않는다.

- **사용자:** 야간 문서처리 자동화를 운영하고 외부 도구 비용까지 책임지는 작은 팀의 개발 리드.
- **계기:** 내부 무료 처리로 끝나지 않아 에이전트가 유료 도구 호출을 요청한다.
- **한 번의 위임:** 공개 합성 PDF 100페이지 → 정해진 열의 CSV 한 개. 허용 판매자 A/B, 총 예산 20 TC, 건별 8 TC, 지정 기한. TC는 테스트 단위다.
- **실패:** 표시 가격 5에 나중에 수수료 7이 붙어 12가 된다. 가격만 승인했는지 최종 청구까지 승인했는지를 대조해야 한다.
- **사용 가능한 결과:** 유효한 CSV 또는 결제하지 않았다는 사유가 있는 중지. 지급과 작업 완료는 다른 상태다.
- **미검증 가설:** 실제 팀에 이런 유료 도구 호출·승인 대조 문제가 반복되는가? 판매자가 확정 가격 API를 제공하는가? 문서처리 수요를 이미 확인한 것으로 취급하지 않는다.

한 팀·한 작업 유형·한 체인·한 결제 자산으로 제한한다. 다중 에이전트 장터, 금융 상품, 보험, DAO, 범용 금융 대시보드는 추가하지 않는다. 기존 TestCredit은 테스트 수단이다.

## 2. 가치의 우선순위

1. **권한:** 승인 밖의 금액·수취인·기한으로 자금이 나가지 않는다.
2. **책임:** 승인한 사람, 판매자가 서명한 가격, 실제 지급, 받은 결과를 구분해 판정한다.
3. **효율:** 알려진 실패를 먼저 검사하되 정상 작업을 과도하게 차단하지 않는다.

Memory는 3번의 조건부 개선이다. 첫 화면은 ‘학습하는 거래 기억’보다 **‘이번 작업에 얼마를 맡겼고, 무엇을 받았는가’**를 보여준다. 모델 가중치가 학습한 것이 아니라 사전 승인된 검사 순서가 바뀐 것이다.

## 3. 블록체인의 역할과 남은 신뢰

DB로 가능한 것은 화면·검색·후보 비교·내부 기록이다. 공개 체인이 추가해야 할 가치는 **운영자 밖에서도 같은 승인 상태를 확인하고, 운영자 코드가 잘못돼도 계약이 정해진 자금 이동을 거부하는 것**이다. 현재 계약은 이 집행을 일부 구현했다. 공개 체인으로 옮겨도 판매자 배송이나 서비스 품질까지 검증되지는 않는다.

- **공개 Sepolia 관통 실행:** 계약 소스/컴파일 설정·배포 주소·승인/결제/취소 tx·관측 블록을 공개한다. Ethereum 문서는 앱 개발에 Sepolia를 안내한다. [공식 문서](https://ethereum.org/en/developers/docs/networks/)
- **백엔드 우회 시험:** 실행자 권한은 있지만 예산을 위반한 직접 호출이 revert하는지 보여준다. 권한 없는 호출의 EXECUTOR_ONLY 거부만으로 예산 집행을 입증하지 않는다.
- **직접 취소:** 현재 `revoke`는 `onlyExecutor`다. 소유자 직접 호출과 유효한 소유자 서명을 가진 제3자 relay를 추가한다. 요청·포함·확정을 구분하며 먼저 확정된 지급을 되돌린다고 표시하지 않는다.
- **서버 없이 감사:** JSON + 별도로 고정한 배포 정보 + 독립 RPC로 검증한다. explorer의 성공 tx만으로 승인 준수 판정을 끝내지 않는다.
- **실패 체크포인트:** 후순위로 중지 사건·통제 요약 hash를 순번·이전 hash와 함께 등록한다. 등록 이후 변경을 드러내며 사건의 진실·누락 없음까지 보장하지 않는다.

계약이 지원하는 금전·정형 조건의 집행과 자연어 선호·실제 품질·오프체인 예약 검사를 구분한다. EIP-712 서명만으로 재사용이 방지되지는 않으므로 nonce·paymentKey·offer digest 검사를 유지한다. [EIP-712](https://eips.ethereum.org/EIPS/eip-712)

실증 절차와 신뢰 경계는 [온체인 검증 계획](ONCHAIN-VALIDATION.ko.md)에 고정했다.

## 4. ‘구매했다’에서 ‘업무를 끝냈다’로 연결

서비스 어댑터는 하나만 만든다. 팀이 운영하는 PDF→CSV 테스트 서비스가 공개 합성 입력을 실제 처리하고 CSV를 생성한다. 외부 상용 판매자 통합은 별도 상태다. 판매자 fixture들은 비교·공격용 시뮬레이터로 표시한다.

문서 인식 모델을 새로 개발하지 않고 기존 변환 엔진에 얇은 구매·작업 어댑터를 붙인다. Qwen은 판매자의 조건 텍스트를 읽으며 문서 이미지 인식을 맡지 않는다. ‘지출을 위임하는 도구’라는 제품 범위를 유지한다.

`quote → payment confirmed → submit job → fetch result → validate result`를 결제와 별도 상태로 관리한다. 승인된 jobSpecHash에 입력 digest·요구 출력 schema·페이지 수를 묶고, 같은 orderId/paymentKey로 결제와 연결한다. 제공 기록에는 output digest·처리량·판매자 서명을 넣는다. 개인정보·원문 PDF는 체인에 올리지 않는다.

결제 후 timeout은 `PAID / DELIVERY_PENDING`, 지급 후 처리 실패는 `PAID / DELIVERY_FAILED`, 결과 schema 오류는 `DELIVERED / VALIDATION_FAILED`다. 같은 idempotency key로 재조회/재전송하며 중복 청구하지 않는다. 환불 자동화는 아직 없으므로 이를 결제 취소나 작업 성공으로 표시하지 않는다. 서명과 hash는 발행자·내용 일치의 증거이며 변환 품질 자체를 보장하지 않는다.

확정 견적 API가 없는 판매자에게 LLM의 추정 가격으로 결제하지 않는다. 어댑터 또는 사람이 확인한 견적이 필요하다. 실제 업체들이 이 방식을 제공하지 않으면 도입 문제를 인정하고 첫 적용을 **자체 운영 유료 도구 게이트웨이**로 제한한다.

## 5. NPU에 의미 있는 일을 맡기고 성과를 측정

현재 정형 가격·수량·환불 선택은 코드 정렬로 상당 부분 대체 가능하다. 협상 요청에 판매자의 최저 수용가를 이미 넣는 구조도 강한 협상 능력의 증거가 아니다.

Qwen의 주 업무를 **비정형 서비스 조건을 사용자 목적과 대조하고 불명확한 조건을 확인하는 일**로 정한다. 예: ‘4시간 내 착수’와 ‘4시간 내 완료’, 이미지 PDF 지원 여부, 재처리와 환불의 차이. 모델은 근거 문구 위치·후보·확인 질문을 제안한다. 미확인 조건을 허용 사실로 바꾸지 않는다. 가격·수량·최종 기한·결제 권한은 승인된 정형 필드와 서명 견적으로 검사한다. 협상은 부가 경로다.

Kiln은 Qwen3-32B의 auto tool calling을 지원하지만 강제/병렬 tool call과 structured output은 지원하지 않는다고 명시한다. 단일 도구 검사와 fail-closed를 유지하고, 확인되지 않은 reasoning 설정의 효과를 약속하지 않는다. [Kiln 모델 문서](https://kiln.bricksum.com/docs/en/models)

두 실험을 분리한다.

| 실험 | 비교 | 판정 |
|---|---|---|
| AI의 필요성 | 규칙 정렬 vs 같은 조건을 읽는 Qwen | 비정형 조건 해석·적격 선택·필요 확인 질문·잘못된 확신·정상 완료율. 정형 부분에서 차이가 없으면 코드로 이동 |
| 통제 순서 | 같은 Qwen·최종 정책의 B0/B1/CM | 성공·과잉 차단·견적 요청·사람 개입·입출력 토큰·지연·실패/통제 생성 비용 |

조건 12개 × 규칙/Qwen 2경로 × 3회 = 72개 관측을 제안하며 실제 Qwen 요청은 36개다. **미실행 계획**이다. 입력·판정·반복·요청 비용 상한을 실행 전에 고정한다. 애매한 조건 4개는 올바른 확인/보류, 명확한 8개는 적격 선택·작업 완료를 각각 평가한다. 보류를 완료율 향상으로 세지 않는다. 이 작은 표본의 지연 p95·평균은 탐색값이다.

현재 48회 결과는 CM의 일반 우월성을 뒷받침하지 않는다. B0 성공 12/16·14,446토큰, B1 9/16·11,760, CM 10/16·12,403이며 CM 생성 비용 1,463토큰이 별도다. 무료·즉시 확정 견적이 지배적이면 B1이 더 단순할 수 있고, Memory를 선택 기능으로 내려야 한다. [원시 결과](../artifacts/experiments/latest.json)

**같은 요청 묶음의 총비용과 올바르게 완료한 업무당 비용을 함께 본다.** 실패·재시도·통제 생성·판매자 요청을 포함한다. 토큰을 줄이려고 정상 요청을 거부하면 개선으로 인정하지 않는다. 승인·영수증 설명·단순 비교에 불필요한 LLM 호출을 더하지 않는다.

NPU 근거도 단계별로 구분한다.

1. 현재 확인: Kiln 모델·generation ID·usage. 사용자의 PC NPU를 구동한 것은 아니다.
2. 확보할 자료: 해당 실행의 backend/hardware route, 모델 artifact·정밀도, 계측 유무에 대한 공급자 자료. 도착하기 전에는 확인됐다고 표시하지 않는다. 자동 연락은 하지 않는다.
3. 가능하면 같은 모델·입출력 길이·품질 기준에서 제공자가 허용한 동시성 1/4/8의 처리량·지연·오류와 에너지를 관측한다. 병렬 API 요청은 동시성 실험이며 NPU batching 직접 제어와 다르다.
4. 계측 창의 총 Joule·올바른 완료 수·idle 처리·공유 배치 할당법을 보고한다. CPU·네트워크·체인을 못 쟀으면 전체 서비스 에너지라고 부르지 않는다. TDP × HTTP 지연은 쓰지 않는다.

Furiosa는 별도 Qwen3-32B/Backend.AI 실험을 공개했다. 조합을 검토할 외부 근거이지 우리 Kiln 요청의 전력 절감률은 아니다. 공급자 계측이 없으면 기존 임의 J/token 예시는 부록에만 두고 발표에는 ‘에너지 미계측’과 실제 토큰을 표시한다. [공식 벤치마크](https://furiosa.ai/blog/white-paper-benchmarking-rngd-on-backend-ai)

## 6. 직관적인 데모

첫 문장은 **“이 문서 100장을 처리하되 수수료까지 8을 넘지 마.”**다. 화면에는 작업, 허용 8, 청구 12, 지급 0이 먼저 보인다. 재시도에서 AI 호출 0을 보여준 다음 정상 6 견적의 실제 결제와 CSV 수령을 보여준다. 마지막에는 원 API 서버를 중지하고 다른 브라우저에서 승인·영수증을 대조한다.

생활 언어 → 결과 → tx/서명 상세 순서다. 주요 행동은 ‘한도 승인 / 실행 / 중지 / 결과 받기 / 영수증 확인’으로 정한다. [4분 스토리보드](DEMO-STORYBOARD.ko.md)는 현재 시연과 목표 시연을 구분한다. 결과물을 만들지 못했으면 CSV 장면을 빼고 현재 크레딧 구매 데모라고 표시한다.

## 7. 개발 순서와 완료 증거

모두 새 기능의 계획이다. 시간 추정 대신 완료 조건으로 관리한다.

| 순위 | 변경 | 대상 | 완료 증거 |
|---|---|---|---|
| P0-1 | 한 작업·한도·결과로 UX 축소 | web, job spec | 처음 보는 3명이 요청/한도/결과를 구분. 관측 전 수치는 미정 |
| P0-2 | owner 직접/서명 relay 취소 | contract v2, wallet/chain adapter | executor 정지 후 취소·이후 지급 거부, 타인 취소·재사용·경합 검사 |
| P0-3 | 공개 Sepolia·독립 검증 | chain adapter, verifier, manifest | 지급+직접 예산 위반 revert+취소 tx, 서버 없이 다른 RPC로 판정 |
| P0-4 | 실제 문서 변환 어댑터 1개 | merchant adapter, job states, receipt | 결제와 CSV digest 연결, 처리량/schema 검사, timeout·중복·결과 오류 경로 |
| P0-5 | 4분 시연·독립 감사 | demo view, verifier UI | 승인·차단·허용·수령·감사 연결. live/기록 재생 구분 |
| P1-1 | 비정형 조건의 Qwen 효용·안정성 | prompt/flow, 평가 fixture | 규칙 기준선과 비교, 실패·usage 전부 보존 |
| P1-2 | NPU 라우팅·효율성 근거 | telemetry, provider evidence | 제공자 확인 수준, 성능/토큰과 실측/가정 에너지 분리 |
| P1-3 | 실패·통제 체크포인트 | checkpoint, verifier | 등록 후 hash 대조, 변조/누락과 사실성 한계 구분 |
| P2 | 제한 고객 pilot·실자산 준비 | 운영·인증·자금·서비스 계약 | 아래 실사용 gate 통과 |

의존 관계: P0-2 → P0-3, P0-1 → P0-4, P0-3 + P0-4 → P0-5. 기존 local 버전을 보존하고 계약/스키마는 새 버전·새 배포로 변경한다. 옛 receipt를 새 도메인으로 재해석하지 않는다.

시간이 부족하면 **공개 독립 검증·직접 취소·정직한 정상/차단 시연**부터 완성한다. 긴 협상·여러 체인·새 통제 유형·장식용 지표를 줄인다. 문서 결과가 없으면 README 기능 선언도 현재 API 크레딧 구매로 유지한다.

## 8. ‘바로 사용 가능’의 단계

| 단계 | 상태 | 허용 범위 |
|---|---|---|
| 로컬 체험 | 현재 가능 | 합성 입력·테스트 자산·한 PC |
| 공개 실증 | 미완료, P0 목표 | 공개 테스트넷·팀 운영 서비스·원 서버 밖 감사 |
| shadow pilot | 미완료 | 동의한 팀의 실제 조건/자료로 판단·증빙을 대조. 실제 지급은 기존 승인 경로. 제품이 실결제를 강제했다고 주장하지 않음 |
| 제한적 실제 지급 | 미완료 | 키 보관·소유자별 자금 회계/출금·결제/제공자 계약·복구·모니터링·보안 검토·손실 한도·수동 대응 확인 후 |

현재 금고는 운영자가 채운 테스트 자금이다. 고객 예치금 소유권·출금·만료 잔액 회수·실제 수수료 예산·환불을 해결한 서비스가 아니다. localStorage 키, 단일 executor/worker, 로컬 DB를 그대로 실자산 서비스에 이식하지 않는다.

8 TC 한도는 판매자의 상품·서비스 수수료 합계다. 체인 가스와 Kiln 추론 비용은 현재 별도 운영 비용이며 호출 횟수 제한이 USD 지출 상한은 아니다. v2 승인 화면에는 누가 각 비용을 부담하는지 분리해 표시하고, 이를 사용자에게 청구하는 버전에는 비용별 예산 예약·가격/환율 기준이 추가로 필요하다.

## 9. 반증과 심사 질문

| 질문 | 답변의 중심 | 주장을 바꿔야 하는 관측 |
|---|---|---|
| DB로 충분하지 않나? | 내부 기능은 가능. 외부 검증과 계약 집행을 별도 시연 | 외부 감사 수요가 없고 모두가 운영자를 신뢰하면 고객용 체인은 선택 옵션 |
| 간단한 예산 지갑 아닌가? | 승인·견적·지급·업무 결과를 같은 건으로 대조 | 고객이 이 연결을 쓸 이유가 없으면 플랫폼 확장 중단 |
| AI가 꼭 필요한가? | 비정형 조건 해석·확인을 기준선과 비교 | 정형 정렬과 차이가 없으면 정렬은 코드로 이동 |
| 왜 NPU인가? | 지정 API의 유효 작업과 품질당 비용·공급자 측정 | 모델명만 있으면 연동 성공까지만 주장 |
| Memory가 더 좋은가? | 반복 실패의 검사 비용을 줄일 수 있는 조건부 방법 | B1이 같거나 우수하면 기본 단순 정책 선택 |
| 거래가 맞으면 문서도 맞나? | 지급 적법성·결과 무결성·품질은 별개 상태 | 결과 검사가 없으면 업무 완료 주장 불가 |

개발 리드 3명에게 최근 실제 유료 도구 사용·승인 대조 사례·견적 API 유무를 확인하는 작은 조사부터 제안한다. 최근 사례가 없고 샘플 제공이나 shadow pilot 의사도 없으면 시장 가설을 강화하지 않는다. 인터뷰·연락은 아직 실행하지 않았다.

**결정:** 주인공은 ‘돈을 맡긴 한 작업이 승인 안에서 끝났는지’다. 블록체인은 권한 집행과 외부 대조, Qwen은 조건 해석, Memory는 조건부 비용 절감이라는 각자의 증거로 평가한다.
