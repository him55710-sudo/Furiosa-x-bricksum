# 첫 사용자를 찾기 위한 근거와 검증

2026-09-28. **공개 자료 조사 완료 / 인터뷰·연락·고객 확보 미실행.** [기획 v3](HACKATHON-PLAN.v3.ko.md)의 대상과 반증 기준이다. 공개 계정의 활동을 개인의 직업·회사 규모·구매 의향으로 확대 추정하지 않는다.

## 누구를 찾을 것인가

유료 검색·본문 API를 리서치봇에 붙인 개발자 중, 결제와 자료 수령이 어긋난 사건을 직접 재현했거나 운영 중인 사람을 우선한다. 지갑·결제 SDK 자체를 만드는 공급자와 그 SDK를 사용하는 고객은 구분한다.

| 후보 집단/공개 접점 | 확인한 신호 | 현재 판정과 확인할 것 |
|---|---|---|
| x402 [#1062 신고자 lpender](https://github.com/x402-foundation/x402/issues/1062) 및 같은 문제 통합자 | 지급 뒤 결과 미수령을 tx와 함께 신고 | 가장 구체적인 역사적 사고 신호. 수정 SDK로 문제가 끝났는지부터 물어야 함. 현재 고객으로 세지 않음 |
| [#3564 작성자 sunruize93-cmyk](https://github.com/x402-foundation/x402/issues/3564) 등 결제 hook 통합자 | HTTP 오류와 지급 관측의 불일치를 로컬로 재현 | 상태 관리에 관심 있는 기술 검증 후보. 실제 손실·리서치 업무·구매 의향 미확인 |
| [x402trace 프로젝트](https://github.com/fardinvahdat/x402trace) | 지급·HTTP 실패 대조 도구와 공개 복구 관측 사례 | 진단 전문가/경쟁·연동 검토 후보. 잠재 유료 고객이라고 단정하지 않음 |
| [Exa x402 사용 개발자](https://exa.ai/docs/integrations/payments/x402/quickstart) | 요청별 검색·본문 구매의 공식 사용 경로 | 제품 사용 맥락은 있음. 반복 장애가 있는 실제 팀을 아직 특정하지 못함 |
| [Firecrawl #3279](https://github.com/firecrawl/firecrawl/issues/3279) 제안 경로 | 요청별 결제 기능 제안 | `closed as not planned`. 도입 완료나 수요 입증으로 사용하지 않음 |

사이트에 나온 로고·예시 지출 표를 실고객 숫자로 세지 않는다. [402.report](https://402.report/)는 지출 통제와 지급 후 오류 타임라인을 소개하므로 경쟁·대체재다. ‘아무도 풀지 않은 문제’라는 주장에 반하는 근거로 사용한다.

## 무엇을 새로 배웠나

최근 대화는 리서치 에이전트의 API 소액 구매, 결정론적 권한, 실패→통제라는 방향을 제시했다. 다만 직업·나이·에이전트 수·구매 빈도·절감 수치는 예시였고 실제 고객 관측이 아니었다.

이번 조사는 더 구체적인 사건을 찾았지만 기존 해법도 확인했다. [x402 #1062의 완료 댓글](https://github.com/x402-foundation/x402/issues/1062#issuecomment-5767578074)은 pending settlement와 자동 복구가 배포되었다고 설명한다. [payment-identifier](https://github.com/x402-foundation/x402/blob/main/specs/extensions/payment_identifier.md)도 이미 요청 재사용을 다룬다. 그래서 **지급 복구 자체를 발명했다고 주장하는 기획은 탈락**시켰다.

다음 단계는 최신 SDK와 영속 상태를 제대로 쓴 뒤에도 남는 문제, 특히 새 실행이 새 구매로 오인되는지와 운영자 밖 검증이 필요한지를 확인하는 것이다. 단순 버전 업그레이드로 해결되는 고객에게 새 금융 시스템을 팔지 않는다.

## 접촉 시 사용할 검증 질문 — 아직 보내지 않은 초안

1. 최근 유료 API 호출 중 ‘지급 여부’와 ‘자료 수령 여부’가 달랐던 사건이 있었나? 익명화한 request/tx/HTTP 기록을 함께 볼 수 있나?
2. 현재 SDK 버전, payment-identifier 사용, shared pending store, outbox, worker 재시작 후 ID 보존 방식은 무엇인가?
3. 같은 자료를 다시 요청할 때 기존 구매 회수와 새 구매를 어떻게 구분하나? 판매자가 회수 API/결과 보관 기간을 약속하나?
4. 그 사건의 실제 추가 지급액·조사 시간·중단된 업무는 얼마였나? 추측과 측정값을 나눠 달라.
5. 별도 계약 검사가 필요한가, DB unique key로 충분한가? 원 운영자 없이 승인과 지급을 검증해야 하는 사람이 실제로 있나?
6. 과거 익명 사건을 로컬 재생해 기존 SDK+DB와 비교하는 30분 검증에 참여할 수 있나? 어떤 결과면 계속 쓰고 싶은가?

관심 있다는 말보다 **재현 기록 제공·재생 참여·후속 사용**을 강한 신호로 본다. 샘플에 비밀키·인증 헤더·개인정보를 요구하지 않는다. 새 연락·메시지는 별도 사용자 지시가 있을 때 실행한다.

## 작게 진행할 검증과 중단 기준

이 수치는 시장 통계가 아니라 팀의 의사결정 기준이다.

- 적합한 개발자 3명과 문제 인터뷰. 적어도 2명이 실제 호출 흐름 또는 익명 사건을 보여줄 수 있어야 한다.
- 그중 1명과 최신 SDK+영속 저장 기준선 재생. 새 결제를 유도하지 않고 과거 사건/합성 fixture로 시작한다.
- 상호 다른 예시에서 재시작→새 ID→추가 지급 가능성 또는 독립 증빙 요구가 확인돼야 다음 연동 개발로 간다.
- 최신 SDK 설정과 DB key만으로 해결되고 독립 집행 수요가 없으면 별도 서비스 가설을 접는다. 유용한 재현/검증 도구로 축소할 수 있다.
- 판매자가 결과 회수를 지원하지 않으면 ‘자동 복구’ 기능은 제공하지 않는다. 고객이 차단·증빙만으로 가치를 느끼는지도 확인한다.

## 아직 모르는 것

실제 반복 빈도, 손실액 분포, 지불 의향, 업체별 recovery 지원률, 당장 연결 가능한 디자인 파트너는 미확인이다. x402 거래 규모로 이를 대체하지 않는다. [2026년 x402 채택 측정 연구](https://arxiv.org/abs/2607.12575)는 온체인 결제 수를 독립적인 이용자 수요로 곧바로 읽기 어렵다고 지적한다. 이 문서는 해당 사전논문의 고객 수 추정치를 채택하지 않는다.

시장성은 해커톤 적합성과 별개다. 지금 확실히 만들 수 있는 것은 좁은 사고의 재현과 통제 증거이며, 사용자가 원한다는 결론은 실제 검증 뒤에 내린다.
