# 데모 v3 — 결제 직후 연결을 끊어보세요

2026-09-28 / **구매 복구 구현용 발표 대본**. 구현은 [구매 복구 실행서](PURCHASE-IMPLEMENTATION.ko.md), 실제 숫자는 [공개 실행 증빙](../artifacts/purchase-sepolia/README.md)을 따른다. 아래 시간은 발표 배분이며 실측 처리시간이 아니다. 별도 Agent Deal Escrow의 release/refund 시나리오와 구별한다.

## 10초 도입

“AI가 자료를 샀습니다. 돈은 나갔는데 응답이 끊겼습니다. 이 봇을 다시 실행하면 또 결제할까요?”

화면에는 기술 지표 대신 한 질문과 네 상태를 둔다.

```text
A사의 외부 게스트는 문서를 편집할 수 있나?

내가 허용한 구매     자료 조회 1회 / 최대 8 TC
지급                확인 중
자료                도착하지 않음
답변                근거를 기다리는 중

[다시 실행]  [중지]  [증빙]
```

TC는 테스트 단위. 판매자는 팀 운영 테스트 서비스. 질문과 문서는 합성 예제. 바깥 경계에 이 세 라벨을 항상 둔다.

## 네 장면

| 목표 시간 | 관객이 보는 행동 | 실제 증거 |
|---|---|---|
| 0:00–0:35 | 질문·조회 1회·8 TC 승인. Qwen이 자료 부족을 판단하고 조회를 제안 | 사용자 서명, purchaseId, 실제 Kiln request ID |
| 0:35–1:25 | 판매자가 6 TC에 제공. 지급 직후 결과 응답 유실 스위치를 누름 | 지급 tx·토큰 이동, 프록시의 응답 차단 기록. 실패를 일으킨 위치 표시 |
| 1:25–2:20 | worker 재시작 후 ‘다시 실행’. 지급 확인→기존 구매 회수 | 같은 purchaseId, 추가 지급 0, 새 run 기록. 새 key/offer 공격은 별도 harness 라벨 |
| 2:20–3:30 | 받은 본문과 근거 답변. 증빙 export 후 원 서버 없이 대조 | 자료 digest·인용 위치, 지급 1회, 서명/계약/tx 연결, 독립 verifier |

공개 Sepolia 실증은 발표 전에 최종 확정까지 마친다. 3분 안에 신규 공개 결제부터 최종 확정까지 끝난다고 약속하지 않는다. 무대에서는 확정된 구매의 응답 유실→실제 worker 재시작→자료 회수를 보여주거나, 같은 run ID의 실제 기록을 명확히 표시해 재생한다. 최초 승인·지급 장면을 녹화 편집할 때는 확정 대기 구간을 생략했다고 표시한다.

시간은 목표이지 API·체인 finality SLA가 아니다. 공개 테스트넷 거래가 늦으면 포함 확인/최종 확정 대기를 표시한다. 이전 확정 실행을 보여줄 경우 run ID와 ‘이전 실제 실행 재생’을 명시하며 신규 tx와 섞지 않는다.

두 번째 실행에는 첫 번째 지급과 다른 offer/payment key로 같은 구매를 지급하려는 공격을 넣을 수 있다. 일반 UI의 재개는 코드가 이를 사전에 막고, 계약 우회 시험은 실행자 지갑에서 보내 실제로 거부되는지 확인한다. 이 공격은 Qwen이 실제로 낸 출력인 것처럼 꾸미지 않는다.

## 성공도 중지도 관객이 이해해야 한다

| 결과 | 사용자 문구 |
|---|---|
| UNKNOWN | “지급 결과를 확인 중입니다. 같은 자료의 새 결제는 보류합니다.” |
| SETTLED / PENDING | “6 TC 지급은 확인했습니다. 자료를 회수하고 있습니다.” |
| SETTLED / RECEIVED | “이전 구매의 자료를 받았습니다. 추가 결제는 없습니다.” |
| SETTLED / UNRECOVERABLE | “6 TC가 지급됐지만 자료를 회수하지 못했습니다. 새 결제는 하지 않았습니다.” |
| DUPLICATE_DENIED | “이 자료 조회는 이미 지급되었습니다. 새로운 실행은 새 구매 허가가 아닙니다.” |
| REVOKED | “권한 취소가 체인에 반영됐습니다. 이전 지급은 유지됩니다.” |

지급·수령·답변 정확성은 별도다. 자료 회수가 안 됐는데 캐시 fixture를 성공 결과로 대신 넣지 않는다. 판매자의 결과 캐시가 살아 있는 조건에서만 복구 성공을 보여준다.

## 필수 경계 시험과 보조 장면

- 동일 작업의 별도 실행에서 5+수수료 7=12 TC가 건별 8 TC를 넘으면 지급 0과 이유를 남긴다.
- 허용 목록 밖 판매자는 지급 0과 이유를 남긴다.
- API 서버를 끈 뒤 소유자가 직접 권한을 취소한다. 별도 미지급 구매로 시연하여 이미 완료된 구매의 중복 거부와 취소 거부를 혼동하지 않는다.
- 감사자는 승인 원문·서명·자료 사본·고정 배포 manifest·독립 RPC로 판정한다. 변경된 자료는 불일치, 누락은 판단 불가. JSON 자기 hash 일치만으로 외부 검증 성공이라 하지 않는다.

심사 제출 파일은 하나의 인덱스로 묶는다: source commit, deployment/code hash, purchaseId, run IDs, quote, consent, payment tx, fault injection, restart log, recovery log, result digest, verifier result, 각 Qwen flow usage. 블록체인은 지급과 binding을 증명하며 자료 내용의 진실·공급자의 이행을 보증하지 않는다.

## 비교 화면에서 하지 않을 연출

기존 x402가 무조건 중복 지급한다고 표시하지 않는다. 최신 SDK·payment-identifier·pending recovery와 영속 DB를 갖춘 기준선부터 비교한다. 의도적으로 새 승인을 만드는 취약 harness는 ‘공격 재현’이다. 정상 통합보다 낫다는 실측 전에는 절감률·고객 손실 예방액·NPU 전력 이득을 숫자로 쓰지 않는다.

핵심 표시는 **같은 구매 승인 / 재시작 / 실제 지급 횟수 / 받은 자료** 네 가지다. B0/B1/CM 연구, 공급자 위험 점수, 전체 에이전트 대시보드는 이 장면 뒤의 부록으로 옮긴다.
