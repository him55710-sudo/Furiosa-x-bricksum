# 구매 단위와 데이터 단위를 분리한 회귀 확인

2026-09-29 KST. 원본 PDF 작업 화면의 실제 Qwen 응답은 구매 가격 180 minor를 설명하면서 KRW라고 표현했다. 계약과 지급은 처음부터 DEMO 정수 단위로 집행됐지만, 사용자가 읽는 설명은 틀렸다. 그 기록은 수정하거나 삭제하지 않았다.

## 변경과 실제 응답

견적 선택·협상·최종 수락 판단에 신뢰된 결제 문맥을 넣었다. `100 minor = 1 DEMO`, `180 minor = 1.80 DEMO`이며, KRW·billion은 납품할 재무 데이터의 단위다. 호출자가 다른 `payment_context`를 넣어도 코드의 결제 문맥을 덮어쓰지 못한다. JSON 도구의 가격 필드에도 같은 단위를 명시했다. 데이터 추출 도구는 별도 KRW/billion 스키마를 유지한다.

[단일 실제 호출 보고서](../artifacts/deal-escrow/unit-regression/2026-09-28T18-10-42.043Z/report.json)에서 `qwen3-32b`는 primary-reports의 210 minor가 건별 한도 200을 넘는다고 설명하고, **180 (1.80 DEMO)**를 제안했다. 실제 정책 함수가 제안을 허용했고 결과 Deal의 자산은 `DEMO`, 가격은 `180`이었다.

| Flow | 호출 | 입력 | 출력 | 합계 | API 지연 |
|---|---:|---:|---:|---:|---:|
| Buyer offer comparison | 1 | 1,063 | 1,418 | 2,481 | 20,229 ms |

이 실행은 기존 사례에 합성 위임 시간을 설정한 개발 회귀다. 새 구매 승인을 받았거나 실제 결제를 한 실행이 아니다. 엔진·지갑·결제 API를 열지 않았으며, 요청 계획과 소스 지문은 호출 전에 저장했다. 자동 재시도는 없다. 원응답·사용량·정책 판정·요청 해시를 보존한다.

한 응답이 올바르다는 사실은 모든 설명이 정확하다는 보장이 아니다. 이전 1,481토큰보다 적은 추론을 썼다는 주장도 하지 않는다. 서로 다른 시점의 두 응답만으로 비용·지연·전력의 인과 효과를 추정하지 않는다.

## 회귀 검사와 운영 반영

자동 검사에서는 의도적으로 `pay 180 KRW`라는 설명을 출력시켜도 코드가 정수 180과 `DEMO` 자산을 유지하는지 확인한다. 허용하지 않은 `currency` 필드를 모델이 추가하면 스키마에서 거부한다. 이는 설명의 사실성 검사와 금전 권한 검사가 서로 다르다는 시험이다.

```powershell
# API 호출 없이 실행 계획만 확인
node scripts/probe-deal-research-units.mjs
# 설정된 Kiln을 한 번 실제 호출; 송금 없음
node --env-file-if-exists=.env.local scripts/probe-deal-research-units.mjs --live
```

3415번 작업 서버에 미정산 거래·진행 중 모델 요청이 없음을 확인한 뒤 새 코드로 재시작했다. 기존 환불·지급 거래는 유지됐고 두 영수증 모두 다시 `VALID`였다. 작업공간의 이전 1회·1,481토큰 기록에 이 별도 시험을 합쳐 하나의 구매 흐름처럼 표시하지 않는다.
